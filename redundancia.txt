CREATE DATABASE IF NOT EXISTS tienda_demo;
USE tienda_demo;

-- Tabla padre
CREATE TABLE categorias (
  id_categoria INT AUTO_INCREMENT PRIMARY KEY,
  nombre       VARCHAR(60) NOT NULL
);

-- Tabla hija
CREATE TABLE productos (
  id_producto  INT AUTO_INCREMENT PRIMARY KEY,
  id_categoria INT NOT NULL,
  nombre       VARCHAR(80) NOT NULL,
  precio       DECIMAL(10,2) NOT NULL,
  stock        INT NOT NULL,
  activo       TINYINT(1) NOT NULL
);

-- Relación (clave foránea)
ALTER TABLE productos
  ADD FOREIGN KEY (id_categoria)
  REFERENCES categorias(id_categoria);

Modo redundante (qué es y por qué es problema)

En un diseño redundante guardas el mismo dato repetido en varias filas/tablas. Ejemplo típico: en productos guardas categoria_nombre en texto (“Periféricos”) en vez de guardar solo id_categoria.

Eso causa:

Inconsistencia: si cambias “Periféricos” a “Accesorios” puedes actualizar algunas filas y otras no → quedan categorías mezcladas.

Más mantenimiento: un cambio simple requiere muchos UPDATE.

Errores por escritura: “Perifericos”, “Periféricos”, “Periféricos ” (espacio) terminan siendo “categorías distintas”.

Más espacio y peor performance en búsquedas/ordenamientos por texto repetido.

Solución (normalización con relación)

Separar la entidad:

categorias(id_categoria, nombre)

productos(id_producto, id_categoria, ...)

Y relacionarlas con FK (productos.id_categoria -> categorias.id_categoria).

Beneficios:

Una sola fuente de verdad: el nombre de la categoría se cambia una vez.

Integridad: no puedes insertar un producto con una categoría inexistente.

Datos limpios y consistentes: adiós duplicados por typos.

Escala mejor: consultas y mantenimiento más simples.
